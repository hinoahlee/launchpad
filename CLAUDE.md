# CLAUDE.md

**Follow [docs/roadmap/rules.md](docs/roadmap/rules.md).** It defines how phases and steps run, the PR flow,
safety rules and code conventions. During a phase, read only that phase's file in `docs/roadmap/phases/`.

## Project map
- `docs/roadmap/`: the plan (`README.md` status table, `rules.md`, `phases/`)
- `docs/glossary.md`: every term introduced so far
- `docs/deploy-contract.md`: what every platform relies on (image, commands, env, probes, signals)
- `docs/decisions/`: decision notes (`NNN-title.md`, from `000-template.md`)
- `docs/runbooks/`: step-by-step procedures for operating production (e.g. `restore-database.md`, `incident.md`)
- `docs/postmortems/`: one five-line file per incident (`YYYY-MM-DD-slug.md`)
- `.github/pull_request_template.md`: the PR description format
- `apps/api`: Fastify API. `config.ts` (env, Zod) → `app.ts` (`buildApp`, routes under `/api`) → `server.ts`
  (listen, signals). In dev the server runs `.ts` directly with Node; the worker runs with tsx (`dev:worker`),
  since it loads `.tsx` email templates. `pnpm build` bundles `server`, `worker`, `migrate` into `dist/` with tsdown.
- `apps/web`: Vite + React SPA. In dev, Vite proxies `/api` to the API (one origin, as in production).
  `src/routes/` (TanStack Router file routes; `routeTree.gen.ts` is regenerated by Vite and committed, as
  TanStack recommends), TanStack Query for server data via `lib/api.ts` (parses with `@launchpad/shared`),
  Tailwind tokens in `index.css`, the product's name/tagline/contact in `lib/site.ts`. UI components come from the shadcn CLI, never by hand:
  `pnpm --filter @launchpad/web exec shadcn add <name>`. The CSP allows no inline scripts or styles.
- `apps/api/src/lib/jobs`: background jobs. Job types and their Zod payloads in `job-types.ts`;
  `enqueue(tx, type, payload)` inside the transaction that saves the job's data (`jobs` table in `@launchpad/db`).
  One handler per type in `handlers.ts` (must be idempotent); `queue.ts` claims/finishes rows; `worker.ts` runs the loop.
  Recurring jobs: add to `schedules.ts` (cron, UTC); `scheduler.ts` queues each run once via `enqueueOnce`.
- `apps/api/src/features/auth`: Better Auth (decision 009) at `/api/auth/*`: `auth.ts` (`createAuth`, on `app.auth`),
  `routes.ts` (Fastify ↔ web `Request`/`Response`). Its tables (`users`, `sessions`, `accounts`, `verifications`)
  are in `@launchpad/db`'s schema; a test fails if they drift from what Better Auth expects.
  Email codes (`emailOTP` plugin): the code is queued as a `sign-in-code` `send_email` job; a first sign-in
  creates the user. In dev without Resend, the worker logs the email's text (the code).
  Google sign-in when `GOOGLE_CLIENT_ID` + `GOOGLE_CLIENT_SECRET` are set. Failed callbacks redirect to
  `/sign-in?error=<code>`. Web: `apps/web/src/features/auth` (session query, sign-in card, header menu), the
  shapes it reads in `@launchpad/shared` (`auth.ts`).
  Protected routes: add `requireSession` (`features/auth/require-session.ts`) as an `onRequest` hook in the
  route's plugin (401 without a session), read the user with `sessionOf(request)`, and filter every query on
  that user's id (another user's row → 404). Example: `features/account` (list and revoke your sessions).
  Web: a route's `beforeLoad` redirects visitors to `/sign-in?redirect=<path>` (`routes/account.tsx`).
- `apps/api/src/lib/email`: send email by queuing `send_email` (payload: `messages.ts`), never by calling a driver
  from a request. `EmailDriver` (`driver.ts`) with adapters: memory (tests), log (no provider set),
  Resend (`RESEND_API_KEY` + `EMAIL_FROM`; `create-driver.ts` picks one).
  React Email templates in `templates/*.tsx`, rendered by `render.tsx` in the worker only. The dev server runs
  on plain Node, which can't load `.tsx`: nothing the server imports may import a template.
  Suppression: `POST /api/webhooks/resend` (`features/email-webhooks`, signature checked by `webhook-signature.ts`)
  records hard bounces and complaints in `email_suppressions`; `send_email` skips those addresses.
- `packages/shared`: the API contract (Zod schemas for every request/response both apps exchange).
- `packages/db`: Drizzle schema (`src/schema.ts`), client, `runMigrations`; SQL migrations in `migrations/`
  (generated, reviewed, committed; shipped inside the package). The API bundles its code; `apps/api/src/migrate.ts`
  is the one migrate entrypoint (deploy: `node dist/migrate.js`; dev: `pnpm db:migrate`). Test helpers
  (`@launchpad/db/testing`): `_test`/`_e2e`-only guard (`assertDisposable`), schema reset, `truncateAll`, factories like `insertUser`.
- `e2e`: Playwright tests (phone + desktop) against the production server (`apps/api/dist/server.js` serving
  the web build, real CSP). Import `test`/`expect` from `#support/fixtures.ts`: any console error fails a test.
- `packages/tsconfig`: shared strict TS configs (`base.json` for Node, `react.json` for the web app)
- References (read-only): `../turborepo`, `../mixmallow`

## Commands
Run from the repo root.
```bash
pnpm install     # one install for every package
pnpm dev         # turbo: every app in watch mode (web, API server, API worker)
pnpm build       # turbo: build in dependency order (cached)
pnpm typecheck   # turbo: tsc in every package
pnpm lint        # biome check (lint + format check), no writes
pnpm format      # biome check --write: fix formatting and safe lint fixes
pnpm test        # turbo: tests in every package (needs `pnpm db:up`: tests use launchpad_test)
pnpm e2e         # build, then Playwright in a browser on a fresh launchpad_e2e (needs `pnpm db:up`; first time:
                 #   pnpm --filter @launchpad/e2e exec playwright install chromium)
pnpm verify      # lint, then typecheck + test + build + db:check: "is this safe to merge?"
pnpm db:up       # start local Postgres (compose.dev.yml) and wait until it's ready
pnpm db:down     # stop it (data kept in the volume)
pnpm db:generate # schema.ts changed → write the next migration (review the SQL, commit it)
pnpm db:migrate  # apply migrations to DATABASE_URL (apps/api/.env); the same file deploys run
pnpm db:check    # fail if schema.ts has changes no migration covers
pnpm db:studio   # browse the database in the browser
```
Local config: each app's `.env` (copy of its `.env.example`), loaded by `pnpm dev` and the `db:*` scripts. Agents never read `.env`.

Shared versions live in the `catalog:` in `pnpm-workspace.yaml`; packages use `"catalog:"`.

## Git
- `main` is protected: every change is a branch `p<N>.<step>-<slug>` and a squash-merged PR.
- Conventional Commits (`feat:`, `fix:`, `chore:`, `docs:` ...). The agent never merges PRs.
